## ELI5

Today the bot finds documents only by meaning: it compares the "blurbs" of everything it has read and keeps the twelve that read most like the question. Ticket GET-674 and GET-675 have almost the same blurb as GET-673, so when a teammate asked for 673 *by name*, the bot offered 674 and 675 instead. The fix gives the bot a second, simpler sense: when a question NAMES a ticket — typed sloppily or not — look that exact name up. First in the bot's own library, which already files every ticket under its name; the named ticket then leads the answer. If the ticket is too new for the library (the library refreshes every 6 hours), the bot reads that ONE ticket from Jira and says the answer came live from there. If Jira does not hand that ticket back, the bot says so plainly — never a neighbour as a stand-in. Questions that name no ticket behave exactly as before, to the byte.

## Intent (what and why)

**What.**

1. **Extract issue keys from the question, for every configured project key** (the `JIRA_PROJECTS` list — env var NAME only; `.env` is never read). Extraction is tolerant of case and separators: `GET-673`, `GET 673`, `get673`, `Get 673` all mean GET-673. A bare number with no project prefix never becomes a key; a key whose project is not in the configured list is not extracted. Every mentioned configured key is resolved (a question may name more than one).
2. **Named + indexed → first in context.** The mentioned issue's chunks enter the answer context AHEAD of every vector hit, through the one shared answer funnel, so Slack and Telegram both get it.
3. **Named + not indexed → one live read-only fetch.** A read-only fetch of exactly that ONE issue (through the existing shared read-only Jira REST seam — no new auth site, no writes, no project sweep) fills the context, and the answer says it came live. A ticket created minutes ago answers correctly before the 6-hourly sync has seen it. A fetch that errors is answered the same honest way as a miss.
4. **Named + Jira does not return it → honest miss.** An answer that names the key and says it was not found / not visible — never a neighbouring ticket, never vector neighbours dressed up as the answer.
5. **No key in the question → retrieval byte-for-byte unchanged.** Same chunk ids, sources, order and scores as at HEAD for key-free questions; the vector pipeline (expansion, doc-prior, diversity cap) is untouched by this plan.
6. **Tests.** A both-ends test (channel end → retrieval end, stubbed embedder/generator/fetcher) reproducing the repro shape RED at base and GREEN after; plus the must-not-fire cases; fixtures and a stubbed fetcher only — never the live Jira, never the `.env`.

**Why.** The defect is structural, not a tuning accident: measured on the real embedder (2026-10-19), `retrieve()` is pure bi-encoder top-12 with no identifier path — "Can you extract Jira Get 673?" leaves GET-673 out of the top 12 entirely, and bare "GET-673" ranks 4th behind neighbours. The wrong answer was teammate-visible in Telegram and is operator-filed as the T1 stone above. Cost focus: the exact leg is a cheap guard in front of the existing pipeline (an in-memory lookup, or ONE bounded single-issue REST call only when a named key is unindexed) and it removes the re-ask/retry cost of wrong-ticket answers.

**Out of scope.** Any change to the embedder, model, prompt, or the 6 h sync cadence; any write to Jira; Confluence page-id lookup (same shape — file-when-asked); restarting or redeploying the live bot (ship tail).

## Risks

| Risk | Mitigation |
|---|---|
| Extraction over-triggers on prose ("get 673 dollars refunded") | A key requires a configured project prefix adjacent to the number; bare numbers never fire (AC-2, AC-7); the no-key parity receipt holds the untouched path fixed (AC-8) |
| Live fetch slow or failing on the answer path | Bounded to ONE issue, read-only, through the existing fetch seam; a fetch error answers with the same honest not-found / not-visible copy as a miss (AC-6) — never neighbours |
| Configured projects whose keys differ only by case | Normalized keys must match the configured list's own casing exactly after normalization |
| Slack and Telegram drift | Both ends asserted in-suite through the shared funnel (AC-4) |
| Test embedder is the jest hash stub, not the real model | The suite reproduces the repro SHAPE (neighbours outrank the named key at base) rather than exact real-model scores; the real-embedder repro script remains the operator-side sanity check |
