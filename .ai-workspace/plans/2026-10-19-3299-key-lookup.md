## ELI5

Today the bot finds documents only by meaning: it compares the "blurbs" of everything it has read and keeps the twelve that read most like the question. Ticket DEMO-674 and DEMO-675 have almost the same blurb as DEMO-673, so when a teammate asked for 673 *by name*, the bot offered 674 and 675 instead. The fix gives the bot a second, simpler sense: when a question really NAMES a ticket — the label typed whole (`DEMO-673`), or the label preceded by "jira"/"ticket" (`Jira Demo 673`) — the bot looks that exact name up. The word "get" starting an ordinary sentence ("can I demo 2 volunteers?") is not a name, and nothing fires. First the bot checks its own library, which already files every ticket under its name; the named ticket then leads the answer. If the ticket is too new for the library (it refreshes every 6 hours), the bot reads that ONE ticket from Jira — giving up after a few seconds rather than leaving the question hanging — and says the answer came live. If Jira does not hand the ticket back, or is too slow, the bot says so plainly — never a neighbour as a stand-in. Questions that name no ticket behave exactly as before, to the byte.

## Intent (what and why)

**What.**

1. **Extract issue keys from the question, for every configured project key — in identifier shapes only** (the `JIRA_PROJECTS` list — env var NAME only; `.env` is never read). In every shape the project prefix must be a configured key as a standalone token, case-insensitive, not glued to other letters (`demon-673` is not DEMO), and the number a standalone digit run (never part of a longer number, never carrying letters). Three shapes:
   - **Hyphenated `DEMO-673`** (any case): fires unconditionally — a hyphen directly joining a configured project key to digits is unambiguous.
   - **Spaced `DEMO 673` / `Demo 673`, or fused `demo673`** (any case): fires ONLY when a Jira-context word — `jira`, `ticket`, `issue`, or `key`, any case — appears within the 3 tokens immediately BEFORE the project-key token. The context word must PRECEDE the key: English prose puts its nouns after the number ("demo 3 tickets"), so a context word that only follows never fires.
   A bare number with no project prefix never becomes a key; a key whose project is not in the configured list is not extracted. The word-like-key prose class — "Can I demo 2 volunteers to review the doc?", "demo 673 dollars refunded", "I need to demo 3 tickets for the jira talk" — extracts NOTHING. The canonical key uses the configured list's own casing; a question may name more than one key (see 3 for the cap).
2. **Named + indexed → first in context, fixed budget.** The mentioned issue's chunks enter the answer context AHEAD of every vector hit, through the one shared answer funnel, so Slack and Telegram both get it. Budget: at most 3 chunks per named source (its first passages in index order); when several keys are named, their chunks lead in first-mention order; the TOTAL context stays the same topK = 12 as today — named chunks displace the tail of the vector hits, they never grow the context.
3. **Named + not indexed → capped, time-boxed live fetches.** At most 3 distinct keys per question are resolved (first-mention order; keys beyond the third are ignored). Each resolved key that is unindexed gets ONE read-only fetch of exactly that issue (through the existing shared read-only Jira REST seam — no new auth site, no writes, no project sweep), in mention order. Every fetch is time-boxed: 5 seconds per fetch, 10 seconds for the whole live leg of one question; a fetch that exceeds its bound is abandoned and never blocks the answer longer than that. The fetched issue's text fills the context under the same ≤3-chunk budget and is NOT added to the index, and the answer says it came live. A ticket created minutes ago answers correctly before the 6-hourly sync has seen it.
4. **Named + Jira does not return it → honest miss.** An answer that names the key and says it was not found / not visible — and, when the bound expired, that the lookup timed out — never a neighbouring ticket, never vector neighbours dressed up as the answer. An errored fetch is answered the same honest way as a miss.
5. **No key in the question → retrieval byte-for-byte unchanged.** Same chunk ids, sources, order and scores as at HEAD for key-free questions; the vector pipeline (expansion, doc-prior, diversity cap) is untouched by this plan.
6. **Tests.** A both-ends test (channel end → retrieval end, stubbed embedder/generator/fetcher) reproducing the repro shape RED at base and GREEN after; plus the must-not-fire prose cases; fixtures and a stubbed fetcher only — never the live Jira, never the `.env`.

**Why.** The defect is structural, not a tuning accident: measured on the real embedder (2026-10-19), `retrieve()` is pure bi-encoder top-12 with no identifier path — "Can you extract Jira Demo 673?" leaves DEMO-673 out of the top 12 entirely, and bare "DEMO-673" ranks 4th behind neighbours. The wrong answer was teammate-visible in Telegram and is operator-filed as the T1 stone above. The context guard exists because the fixture project key `DEMO` is itself an English word, so separator tolerance must be paid for with a context requirement on the prose-shaped forms — otherwise "can I demo 2 volunteers" pins and fetches DEMO-2 and replaces the real answer (review r1, finding 1). Cost focus: the exact leg is a cheap guard in front of the existing pipeline (an in-memory lookup, or at most 3 time-boxed single-issue REST calls only when named keys are unindexed) and it removes the re-ask/retry cost of wrong-ticket answers.

**Out of scope.** Any change to the embedder, model, prompt, or the 6 h sync cadence; any write to Jira; Confluence page-id lookup (same shape — file-when-asked); restarting or redeploying the live bot (ship tail).

## Risks

| Risk | Mitigation |
|---|---|
| Extraction over-triggers on prose ("demo 673 dollars refunded", "demo 2 volunteers") | Only identifier shapes fire: hyphenated unconditionally; spaced/fused forms additionally require a Jira-context word within the 3 tokens BEFORE the key (AC-2 b/c, AC-7 arms 2–3); bare numbers never fire; the no-key parity receipt holds the untouched path fixed (AC-8) |
| Configured project key is an English word (the fixture key `DEMO` is one) | The context-word guard is applied to the prose-shaped forms for EVERY configured key, word-like or not — no dictionary, uniform rule, conservative direction (a missed loose form falls back to today's vector behavior) |
| Live fetch slow or hanging on the answer path | Time-boxed — 5 s per fetch, 10 s for the whole live leg of a question; expiry routes into the honest timed-out copy naming the key (AC-11), never neighbours, never an unanswered question (the #3286 regression class) |
| Many keys named in one question | Hard cap: 3 distinct keys resolved, first-mention order, ≤ 3 fetches (AC-10 c) |
| Pinned chunks crowd out vector context | ≤ 3 chunks per named source, total context still topK = 12 (AC-4, AC-10 a) |
| Configured projects whose keys differ only by case | Normalized keys must match the configured list's own casing exactly after normalization |
| Slack and Telegram drift | Both ends asserted in-suite through the shared funnel (AC-4) |
| Test embedder is the jest hash stub, not the real model | The suite reproduces the repro SHAPE (neighbours outrank the named key at base) rather than exact real-model scores; the real-embedder repro script remains the operator-side sanity check |
