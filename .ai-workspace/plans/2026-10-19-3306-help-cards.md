## ELI5

On Telegram today EVERY text message — "hi", a bare "/model", anything — is poured straight into the document search and comes back as a cited doc lecture (a greeting got a lecture about introducing yourself; "/model" got the coding-rules page). This plan puts a tiny, word-matching doorman in FRONT of that search on the Telegram path only. If a message is (P1) a Telegram-shaped slash-command token the bot does not answer on Telegram, (P2) just a short hello — said plainly, naming the bot, or @-mentioning it — or (P3) a whole-message cry for help ("help", "what can you do"), the bot replies with ONE fixed capability card: what the bot does and how to ask on THIS surface. The card derives from the same single capability source Slack's `/help` uses, so the shared parts can never drift — but each surface renders only what actually works there: the Telegram card is the shared capability line plus a "just ask a question in plain text" line with examples and NO slash-command list (no slash command works on Telegram), while Slack's `/help` keeps its exact command list. A card never touches retrieval or the LLM (a greeting costs zero tokens). Anything else — including "hi, list the localisation placeholder …", "help me find X", and a pasted path like "/etc/hosts" — walks past the doorman untouched and gets the byte-identical answer it gets today. The operator's researched stance is *teach, don't cater*: no Telegram command handlers are built; the card teaches what the bot is and how to ask.

## Problem (why)

`processUpdate` in src/telegram/adapter.ts routes every allowed text message straight to `handleQuery` — the same doc-Q&A seam Slack uses. There is no Telegram command surface at all (verified: no command registration, no setMyCommands anywhere in src/telegram/), so a greeting or a stray "/model" is searched as a document question: wrong answer, wasted retrieval + LLM tokens, and no way for a Telegram user to discover what the bot does. The fix mirrors the two deterministic routers already shipped: `classifyMentionIntent` (#1344, pure mention classifier in src/slack/commands.ts) and the #3299 exact-key leg (src/knowledge/service.ts) — a pure pre-filter in front of the pipeline whose non-matching branch is byte-identical to today.

## Determined boundaries (and why)

**B1 — Where the gate sits.** Telegram reply path only, inside `processUpdate`, before the `handleQuery` call. The matcher + card builder live in a new pure module under src/telegram/ (no I/O; imports nothing from knowledge/llm), in the shape of `classifyMentionIntent` / `extractIssueKeys`: exported, deterministic, safe-default = doc route (today's behaviour). Slack paths are untouched.

**B2 — Gate order.** (1) unknown slash command, (2) short greeting, (3) whole-message help probe; first match wins. All three yield the same card; the greeting arm prefixes one greeting line.

**B3 — Normalization (gate-internal only).** Start from the message text trimmed exactly as `processUpdate` already trims it. Split on whitespace; DROP tokens that begin with "@" (a mention is a vocative, never question content — "@bot hey" is a pure greeting); strip non-alphanumeric characters from both ENDS of each remaining token (so "hi!" → "hi", "Hello?" → "hello", a pure emoji/punctuation token strips to empty and is dropped — "hi 👋" stays a greeting); case-fold for comparison only. The surviving tokens are the *countable tokens*. The P1 command-shape check (B4) runs on the RAW first whitespace token — lowercased, trailing sentence punctuation stripped, optional `@name` suffix removed — BEFORE end-stripping (end-stripping would eat the leading "/"); the countable-token rules above apply to the greeting and help-probe arms. On any non-match, the doc path receives the ORIGINAL trimmed text byte-for-byte — normalization never leaks into the query (the #3299 parity convention).

**B4 — P1: unknown slash command.** Fires iff the first character of the trimmed text is "/" AND the raw first token is *command-shaped* AND the message is not a *registry command carrying its payload*. Command shape, as Telegram command syntax defines it: the token (lowercased, trailing sentence punctuation "!" "?" "." "," "…" stripped) must FULLY match `^\/[A-Za-z][A-Za-z0-9_-]*(@[A-Za-z0-9_]+)?$` — exactly one leading "/", a letter first, then only letters/digits/dash/underscore, optionally ONE "@bot-username" suffix, at most 32 chars before the suffix. Consequences and justification:
- A token containing any further "/" is NOT a command: "/api/v1/users", "/etc/hosts" are paths, not commands → doc path (a pasted path or slash-prefixed line is a real doc question today). A URL ("https://…") does not begin with "/" and never enters this arm.
- *Registry command carrying its payload* = after stripping the optional @suffix, the command word is an argument-taking registry name from the shared registry {ask, jql, feedback-monday, sync-confluence} AND a non-empty remainder follows it.
- No Telegram commands exist natively (verified), so "/model", "/start", "/foo", "/model@monday_bot" are all unknown → card. "/start" is Telegram's canonical first contact — the card is exactly the right answer there.
- Registry commands WITH their payload ("/ask how many days…", "/jql show me crashes", "/ask@monday_bot how many days…") keep today's byte-identical doc path: they carry a real question today; eating them would regress a live question path.
- Registry commands typed BARE ("/help", "/status-monday", "/HELP") fire the card: on Telegram they have no handler, so today they are doc-search noise; bare command words are precisely the teachable moment, and the card's truthful answer is "no slash commands here — just ask in plain text" (it does NOT re-list the command, so no loop).
- Case-insensitive on the command word; a message whose slash is not leading ("what does /model mean") never fires. v1 does not verify that an @suffix names THIS bot (its username is runtime config): any one @suffix is accepted and stripped — accepted edge, conservative direction (ambiguity → doc) unchanged.

**B5 — P2a: short greeting.** Fires iff countable tokens ≤ 3 AND at least one is in the greeting lexicon AND EVERY countable token is in greeting lexicon ∪ greeting filler. Lexicon (fixed, exported): hi, hello, hey, hiya, howdy, yo, sup, greetings, good, morning, afternoon, evening. Filler (vocative-adjacent, never question content): there, everyone, everybody, team, folks, all, again, bot, PLUS the bot's own name token(s) — "monday", "monday-bot" (an exported constant, B10). So "good morning everyone" fires, "hello monday" fires (the name is a vocative addressing the bot), and the @-mention form needs no lexicon entry at all because B3 drops "@"-prefixed tokens ("hi @monday_bot" counts as the one-token greeting "hi" — whatever username the mention carries). "good bug report" does not fire ("bug" is content). Justification: the all-tokens rule is what provably protects the dispatch's own regression example class — "hi DEMO-673" (2 words, but a real key question) and "hello monday, what about annual leave" ("what/about/annual/leave" are content) keep the doc path; the conservative direction (ambiguity → doc) is the #1344 doctrine.

**B6 — P2b: whole-message help probe.** Fires iff the normalized whole message (countable tokens joined by single spaces, lowercased) EQUALS one of: help, commands, what can you do, what do you do, how does this work. Trailing "?" is handled by punctuation stripping ("What can you do?" fires). Whole-message equality — not substring, not prefix — is the only reading under which "help me find X" and "what can you do about Y" provably keep the doc path.

**B7 — P3: one shared capability source, truthful per surface.** A single exported pure capabilities module becomes the ONLY source of what the bot can do. It holds (1) the command registry, moved verbatim from today's module-private `AVAILABLE_COMMANDS` in src/slack/commands.ts (refactor only — `helpCommand()` delegates to the shared renderer and its output stays byte-identical, golden-tested), and (2) ONE shared capability description — the plain-language "what this bot is and does" text — from which the plain-question capability is derived (ask anything as an ordinary message; example asks drawn from the plan's own arm corpus). Each surface renders ONLY the capabilities available on it: Slack `/help` renders the full command list, byte-identical to today; the Telegram card renders the shared capability description plus the ask-in-plain-text line and examples, and renders NO slash-command token — no slash command works on Telegram, so the card can never teach a command that dead-ends or loops there. The no-drift AC (AC-7) applies to these shared parts: wherever a shared element renders, it renders byte-identical from the single source. The card is plain text — no `Sources:` line, no citations, no context blocks, no parse_mode; the greeting arm prefixes one fixed greeting line, the command/help arms a one-line "here's what I do" lead-in.

**B8 — Zero cost, no logging noise.** Card arms make no `query` call, no LLM call, and skip `recordAsk`: the 2-week ask log tallies retrieval-served asks for the kill rule, and a card is not an ask — keeping the metric meaning "real asks" is what makes the kill-rule honest.

**B9 — Group chats / anti-spam.** No chat-type branching (the minimal `TgUpdate` shape has no chat type; the allow-list already scopes who is served). A card is only ever sent as the `processUpdate` reply to a MATCHING update — one sendMessage per matching update, never proactive, no reply_to threading in v1 (transport `sendMessage` shape unchanged).

**B10 — Config surface.** Lexicons, probe phrases, the greeting-filler name token(s), and card copy are exported constants. NO env overrides in v1 — a deliberate deviation from the `MENTION_*` precedent: cost focus, fewer moving parts; an override knob can follow real demand.

## Must-not-regress

- Any non-matching message → `handleQuery` receives the original trimmed text byte-for-byte, exactly one query call, existing render/split/send path, ask-log line as today (#3299 parity convention).
- The named guards: "hi, list the localisation placeholder in the strings file" and "hi DEMO-673" (greeting-prefixed real questions); "hello monday, what about annual leave" (name + real question); "help me find the localisation placeholder" (help probe with content); "/ask …" / "/jql …" with payload (registry commands); "what does /model mean in the slack adapter" (non-leading slash); the leading-path/URL class "/api/v1/users what does this return", "/etc/hosts", "https://example.com/v1/users what does this endpoint return" (real doc questions today); non-text updates and disallowed chat ids (silence unchanged).
- Slack untouched: `/help` output byte-identical, `classifyMentionIntent` untouched, Slack adapter untouched.

## Named risks (carried from r1 review, kept named)

- **One-word lexicon collisions**: a message consisting solely of a lexicon/filler/probe word — "morning", "good", "sup" (P2a lexicon) or "commands", "how does this work" (P2b probes) — fires the card although it is a plausible whole-message doc query. This is a theorem about finite match sets, not a defect of this plan; the ambiguity→doc doctrine already bounds it. Execution-review condition: tighten (shrink one-word lexicon entries / probe set) ONLY if the shipped sets grow beyond the plan's exported constants or a real ask-log `questionLen` pattern shows one-word doc asks receiving cards — no new AC arms now.
