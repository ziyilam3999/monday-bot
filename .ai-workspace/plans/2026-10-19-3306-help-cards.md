## ELI5

On Telegram today EVERY text message — "hi", a bare "/model", anything — is poured straight into the document search and comes back as a cited doc lecture (a greeting got a lecture about introducing yourself; "/model" got the coding-rules page). This plan puts a tiny, word-matching doorman in FRONT of that search on the Telegram path only. If a message is (P1) a slash-command the bot does not answer on Telegram, (P2) just a short hello, or (P3*) a whole-message cry for help ("help", "what can you do"), the bot replies with ONE fixed capability card — the same command list Slack's `/help` shows, from one shared source so the two can never drift — and never touches retrieval or the LLM (a greeting costs zero tokens). Anything else, including "hi, list the localisation placeholder …" and "help me find X", walks past the doorman untouched and gets the byte-identical answer it gets today. The operator's researched stance is *teach, don't cater*: no Telegram command handlers are built; the card teaches what the bot is and how to ask.

## Problem (why)

`processUpdate` in src/telegram/adapter.ts routes every allowed text message straight to `handleQuery` — the same doc-Q&A seam Slack uses. There is no Telegram command surface at all (verified: no command registration, no setMyCommands anywhere in src/telegram/), so a greeting or a stray "/model" is searched as a document question: wrong answer, wasted retrieval + LLM tokens, and no way for a Telegram user to discover what the bot does. The fix mirrors the two deterministic routers already shipped: `classifyMentionIntent` (#1344, pure mention classifier in src/slack/commands.ts) and the #3299 exact-key leg (src/knowledge/service.ts) — a pure pre-filter in front of the pipeline whose non-matching branch is byte-identical to today.

## Determined boundaries (and why)

**B1 — Where the gate sits.** Telegram reply path only, inside `processUpdate`, before the `handleQuery` call. The matcher + card builder live in a new pure module under src/telegram/ (no I/O; imports nothing from knowledge/llm), in the shape of `classifyMentionIntent` / `extractIssueKeys`: exported, deterministic, safe-default = doc route (today's behaviour). Slack paths are untouched.

**B2 — Gate order.** (1) unknown slash command, (2) short greeting, (3) whole-message help probe; first match wins. All three yield the same card; the greeting arm prefixes one greeting line.

**B3 — Normalization (gate-internal only).** Start from the message text trimmed exactly as `processUpdate` already trims it. Split on whitespace; DROP tokens that begin with "@" (a mention is a vocative, never question content — "@bot hey" is a pure greeting); strip non-alphanumeric characters from both ENDS of each remaining token (so "hi!" → "hi", "Hello?" → "hello", a pure emoji/punctuation token strips to empty and is dropped — "hi 👋" stays a greeting); case-fold for comparison only. The surviving tokens are the *countable tokens*. On any non-match, the doc path receives the ORIGINAL trimmed text byte-for-byte — normalization never leaks into the query (the #3299 parity convention).

**B4 — P1: unknown slash command.** Fires iff the first character of the trimmed text is "/" AND the message is not a *registry command carrying its payload*: i.e. NOT (first token — lowercased, trailing punctuation stripped — is an argument-taking command name from the shared registry {ask, jql, feedback-monday, sync-confluence} AND a non-empty remainder follows it). Consequences and justification:
- No Telegram commands exist natively (verified), so "/model", "/start", "/foo" are all unknown → card. "/start" is Telegram's canonical first contact — the card is exactly the right answer there.
- Registry commands WITH their payload ("/ask how many days…", "/jql show me crashes") keep today's byte-identical doc path: they carry a real question today and semi-work today; eating them would regress a live question path and would teach-then-loop (the card lists "/ask <question>"; following that instruction must still reach an answer path, not another card).
- Registry commands typed BARE ("/help", "/status-monday", "/HELP") fire the card: on Telegram they have no handler, so today they are doc-search noise; bare command words are precisely the teachable moment.
- Case-insensitive on the command token; a message whose slash is not leading ("what does /model mean") never fires.

**B5 — P2a: short greeting.** Fires iff countable tokens ≤ 3 AND at least one is in the greeting lexicon AND EVERY countable token is in greeting lexicon ∪ greeting filler. Lexicon (fixed, exported): hi, hello, hey, hiya, howdy, yo, sup, greetings, good, morning, afternoon, evening. Filler (vocative-adjacent, never question content): there, everyone, everybody, team, folks, all, again, bot. So "good morning everyone" fires; "good bug report" does not ("bug" is content). Justification: the all-tokens rule is what provably protects the dispatch's own regression example class — "hi DEMO-673" (2 words, but a real key question) keeps the doc path, and the conservative direction (ambiguity → doc) is the #1344 doctrine.

**B6 — P2b: whole-message help probe.** Fires iff the normalized whole message (countable tokens joined by single spaces, lowercased) EQUALS one of: help, commands, what can you do, what do you do, how does this work. Trailing "?" is handled by punctuation stripping ("What can you do?" fires). Whole-message equality — not substring, not prefix — is the only reading under which "help me find X" and "what can you do about Y" provably keep the doc path.

**B7 — P3: one shared card.** Today's module-private `AVAILABLE_COMMANDS` registry in src/slack/commands.ts becomes the single source for BOTH the Slack `/help` text and the Telegram card body: one exported pure builder renders the command list; `helpCommand()` delegates to it and its output stays byte-identical (refactor only, golden-tested); the Telegram card is that same command-list body, optionally prefixed by one fixed preamble line per arm (greeting arm: a greeting; command/help arms: a here's-what-I-can-do line that also says questions work as plain messages). The card is plain text — no `Sources:` line, no citations, no context blocks, no parse_mode.

**B8 — Zero cost, no logging noise.** Card arms make no `query` call, no LLM call, and skip `recordAsk`: the 2-week ask log tallies retrieval-served asks for the kill rule, and a card is not an ask — keeping the metric meaning "real asks" is what makes the kill-rule honest.

**B9 — Group chats / anti-spam.** No chat-type branching (the minimal `TgUpdate` shape has no chat type; the allow-list already scopes who is served). A card is only ever sent as the `processUpdate` reply to a MATCHING update — one sendMessage per matching update, never proactive, no reply_to threading in v1 (transport `sendMessage` shape unchanged).

**B10 — Config surface.** Lexicons, probe phrases, and card copy are exported constants. NO env overrides in v1 — a deliberate deviation from the `MENTION_*` precedent: cost focus, fewer moving parts; an override knob can follow real demand.

## Must-not-regress

- Any non-matching message → `handleQuery` receives the original trimmed text byte-for-byte, exactly one query call, existing render/split/send path, ask-log line as today (#3299 parity convention).
- The named guards: "hi, list the localisation placeholder in the strings file" and "hi DEMO-673" (greeting-prefixed real questions); "help me find the localisation placeholder" (help probe with content); "/ask …" / "/jql …" with payload (registry commands); "what does /model mean in the slack adapter" (non-leading slash); non-text updates and disallowed chat ids (silence unchanged).
- Slack untouched: `/help` output byte-identical, `classifyMentionIntent` untouched, Slack adapter untouched.
