## ELI5

Since #3299, when a teammate asks about a ticket BY NAME ("Can you extract Jira DEMO 673?"), the bot finds exactly that ticket and retells its title, story, acceptance criteria and technical note. But it ends with an apology: status, assignee and priority are "not in my context" — because they genuinely aren't anywhere. The library copy (the 6-hourly sync) never asked Jira for them, and the live one-ticket read #3299 added asks for the same three things only. So when a teammate asks "what is the status of DEMO-673?", the honest bot still can't answer. The fix: the one-ticket live read now also asks for the ticket's status, assignee, priority, resolution and last-updated — the same single read, five more field names — and the bot shows them as a short facts line it assembles itself (never the model guessing): "DEMO-673 — Status: In Progress · Assignee: Display Name · Priority: High · Updated: 2026-10-18, fetched from Jira just now." The facts are LIVE, not library copy, precisely because status is the field that goes stale fastest — a 6-hour-old status is the wrong answer. Empty slots are said plainly ("Unassigned", "not set"), never invented. If the live read fails or is too slow, the bot says it couldn't get the current facts — while still retelling the ticket from the library. Nothing else changes: questions that name no ticket behave exactly as before, to the byte, and the sync itself is untouched.

## Intent (what and why)

**What.**

1. **The metadata comes from the #3299 bounded live fetch — the sync is NOT widened.** Where the fields live today: nowhere. The knowledge sync DROPS them at fetch time — `buildJiraFetcher` requests `fields=summary,description,comment` (src/jira/sync.ts:254), `toJiraIssue` maps none of them, and the indexed body is `[key, summary, descriptionText, ...commentTexts]`; the #3299 one-issue fetcher requests the same three fields (src/jira/sync.ts:281) and `LiveIssue` (src/knowledge/service.ts) carries no metadata. So the dispatch's first option — "from the synced index if the sync already stores those fields" — is factually unavailable, and the plan takes the second: the bounded live fetch. Only the ONE-ISSUE fetcher's field list grows (`status,assignee,priority,resolution,updated` added to the same GET — same shared `fetchPaginatedIssues` seam, same JQL, same maxResults 1, same 5 s per-fetch / 10 s per-leg boxes, still read-only). The knowledge-sync fetcher, the open-defects fetcher and the NL→JQL fetcher keep their byte-identical field lists and URL contracts.
2. **Prefer live, for every key the exact-key path resolves — indexed or not.** When a named key is INDEXED, its pinned chunks still come from the index (title/story/AC, citations, no change), but ONE bounded live fetch of that same key supplies the facts line — because an indexed status is up to 6 hours stale, and stale status is exactly the defect. When the key is UNINDEXED, the existing #3299 live fetch (now field-widened) supplies both the pinned text and the facts line — one fetch, never two. At most 3 keys per question, first-mention order, inside the existing sequential leg and its deadline; no new budget class. The line is assembled by CODE from the fetched fields (the #3299 prelude pattern), never left for the model to infer: `DEMO-673 — Status: … · Assignee: … · Priority: … · Resolution: … · Updated: …`, plus a live note ("fetched from Jira just now"). Resolution and last-updated ride along when present (cheap: same GET); an unresolved issue says "Unresolved", an unassigned one "Unassigned", a genuinely absent field is omitted or said plainly ("not set") — never guessed, never a placeholder dressed as a value.
3. **Freshness is stated, not implied.** Live values are labelled live. The issue's own `updated` timestamp is both an answer field and the honesty bound on the line. Nothing indexed is ever presented as the CURRENT status. The existing "fetched live … (created too recently for the 6-hourly sync)" prelude copy stays truthful: that reason holds for unindexed pins; for an indexed key the new facts line carries its own live note — no copy claims an indexed key was "created too recently".
4. **Live-facts failure is honest, and the pin survives.** If the facts fetch misses, errors or times out for an INDEXED key, the answer keeps the pinned-chunk retelling AND adds one plain line ("current status/assignee/priority for DEMO-673 could not be fetched") — no facts value appears. The all-miss honest-answer path of #3299 (every named key a miss → the naming-the-key answer, no generator call) is unchanged. With NO fetcher configured (Jira creds absent), an indexed named key gets exactly today's pinned answer — no facts line, no "unavailable" line (the #3299 "skipped" semantics: absent Jira must not fabricate a not-found).
5. **Privacy: display name only.** The assignee renders as `fields.assignee.displayName` and nothing else; the mapper never reads `emailAddress` (or any other assignee property), so an email cannot leak into an answer. This exposes nothing the issue tracker doesn't already show the same chat; no other personal data is introduced.
6. **Non-key parity (#3299 AC-8 convention).** A question that names no configured key takes the untouched branch: same chunk ids, sources, order and scores, same answer and citations, byte-identical — verified against a service constructed without `issueLookup`.
7. **No re-sync after deploy — there is no operator-run step.** Nothing about the index, the sync's field list, or its URL changes, so deploy alone is sufficient; the scheduled 6-hourly sync continues untouched and is not relied upon for this feature. (Recorded explicitly because the dispatch asks: re-sync NOT needed; NOT operator-run.)
8. **Tests.** A new sibling suite `tests/key-lookup-meta.test.ts` through the shared funnel (`KnowledgeService.query`) with a stubbed generator and a stubbed/injected read-only fetcher (the real mapper exercised via a fake `fetchImpl` for the privacy arm), checked-in fixtures under `tests/fixtures/key-lookup/` — DEMO project key only, no network, no `.env`. It compiles and RUNS at pristine origin/master (lazy `require` / type-erased factory for any symbol that does not exist there, per the #3299 RED-at-base discipline) with the must-fire arms failing there.

**Why.** The defect is a data gap, not a ranking bug: #3299 pinned the right ticket but the fields users ask about next were never fetched on any path. Live-preferred is the cheap correct shape: the alternative (widening the sync) needs a full re-index to take effect, lands up to 6 hours stale on arrival, still needs a live leg for freshness-sensitive asks, and touches a URL contract the tests lock. Cost focus: the only new spend is one bounded single-issue GET per named key (≤3 per question, time-boxed) on the rare exact-key path — against the re-ask cost of "the bot can't tell me the status of the ticket it just quoted".

**Out of scope.** Storing metadata in the index or widening any sync fetcher; changing the embedder, prompt or the 6 h cadence; Confluence metadata; any write to Jira; restarting or redeploying the live bot (ship tail).
