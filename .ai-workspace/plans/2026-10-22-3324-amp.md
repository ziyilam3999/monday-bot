## ELI5

When the bot answers with sources, the Slack formatter carefully "HTML-escapes" each source title (`&` becomes `&amp;`, `<` becomes `&lt;`) because Slack's API demands it — and Slack un-does that on display, so Slack users see a normal `&`. The Telegram reply reuses those same already-escaped lines but never un-escapes them, and Telegram sends plain text (no decoding, no markup). So a Telegram user sees the plumbing: "General Dispute Resolution &amp; Customer Support". The fix teaches the Telegram render step to un-do exactly the escaping the Slack formatter applied — nothing more — so every surface shows the title's plain characters exactly once: the same title shows `&` on Slack AND `&` on Telegram, and a title that genuinely contains the literal text `&amp;` still shows `&amp;` (un-escaping runs exactly once, never twice). Telegram messages are plain text by design, so restored `<`, `>`, quote characters cannot break the message format, and the emphasis-stripping that already runs keeps any title's stray markup characters from altering the reply's shape.

## Problem (why)

Field report (2026-10-22, real Telegram reply): a Sources line shows `General Dispute Resolution &amp; Customer Support`. Chain, verified in code and by fixture:

1. Citation titles (headings from wiki pages, tracker summaries) reach `formatAnswer` as plain text (`&` intact) — Confluence/jira/wiki ingestion stores them plain (`stripHtml` in src/confluence/sync.ts decodes bodies; markdown headings are taken as written).
2. `sanitizeTitle` (src/slack/formatter.ts:73) escapes `& < >` for Slack's API — correct there, Slack decodes on display.
3. `renderTelegramReply` (src/telegram/formatter.ts:20) reuses the Slack context elements and strips only mrkdwn `*x*` pairs — the entities survive verbatim, and the transport sends plain text with NO parse_mode (src/telegram/transport.ts:82), so nothing ever decodes them. Telegram users see the raw entity.

Fixture repro (tmp/repro-3324.cjs, compiled pure formatters only — no model, no network): `formatAnswer` with heading `General Dispute Resolution & Customer Support` → Slack element `*[1]* confluence:DEMO-1 — General Dispute Resolution &amp; Customer Support` → Telegram reply line `[1] confluence:DEMO-1 — General Dispute Resolution &amp; Customer Support`; heading `Refund policy: "fast" <v2> track` → `&lt;v2&gt;` on Telegram. Exactly the field report.

## Determined boundaries (and why)

**B1 — Where the fix sits.** The un-escape lives at the single Slack→Telegram boundary: the citation context element texts inside `renderTelegramReply` (src/telegram/formatter.ts) — the one function every Telegram reply render goes through (adapter line ~196 and the help-gate test seam both call it). Slack's `sanitizeTitle` stays exactly as-is (Slack's API requires those escapes). One code file changes; no adapter, transport, or Slack-side edit.

**B2 — Decode set and arity.** The decode is the exact inverse of `sanitizeTitle`'s encode set — `&lt;`, `&gt;`, `&amp;` (ampersand last, mirroring the encode order) — applied ONCE per string. Nothing outside that set is ever decoded (`&quot;`, `&#39;`, `&nbsp;` pass through untouched: quotes were never encoded, so decoding them would corrupt source text). This gives round-trip identity: render(sanitize(s)) ≡ s for every string s — the property AC-4/AC-5 pin.

**B3 — Scope: citation lines only, never the body.** The answer body (`payload.text`) never passes through `sanitizeTitle` (the markdown→mrkdwn converter escapes nothing), so it needs no decode; a model answer legitimately containing a literal entity stays as written. The decode applies to context-element text as a class — source, heading, and any future producer that adds context lines — so coverage is by position at the boundary, not by enumerating today's producers.

**B4 — Safety is by construction, and stays pinned.** Telegram transport sends plain text with no parse_mode, so restored `<`/`>`/`&` cannot break message format. `sanitizeTitle` strips `* ~ ` and backtick from titles BEFORE escaping, and the decode restores only `& < >`, so decoding can never resurrect emphasis pairs; the existing mrkdwn-strip and `splitMessage` behavior are pinned unchanged by AC-6. If a future change adds a Telegram parse_mode, this boundary must be revisited (named risk below).

**B5 — Ingestion is out of scope.** The render-layer contract is byte-identity with the indexed title text. If an upstream source ever delivers a PRE-escaped title (Confluence page titles bypass `stripHtml`, which decodes only bodies), both surfaces would faithfully show the stored entity — that is an ingestion gap, not a render bug, and gets its own ticket if ever observed in the ask log or a field report (execution-review condition; no AC arm now).
