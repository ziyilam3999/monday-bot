## ELI5

The bot has a fast lane for questions that name a ticket: it reads that exact ticket live from Jira and says its current status. To avoid mistakes, it only treats "get 673" (with a space, no dash) as a ticket name when a word like "jira" or "ticket" comes just before it — because "get" is also an everyday verb ("can I get 2 volunteers?"). The operator asked "what's the status of get 673?". No "jira" or "ticket" word, so the fast lane never opened; the question went to the ordinary search, which had no passage about GET-673, and the bot said it couldn't find it. The ticket is real (Jira returns it). The fix: a question that asks for a ticket's status / assignee / priority ("status of get 673") counts as enough context, while "can I get 2 volunteers" still does not.

## Root cause

The loose (spaced) shape `get 673` is gated on a context word from `{jira, ticket, issue, key}` before the key; the operator's question carries a status cue ("status of") but none of those words, so `extractIssueKeys` returns `[]` and the exact-key leg never runs.

Alternatives ruled out by evidence:
- **Project-key allowlist** — ruled out: `GET` is configured (`GET_configured=true`, startup log `jira:GET indexed 898 issues`), and `get-673` / `status of jira get 673` both extract `GET-673`.
- **Jira fetch failure** — ruled out: the fetcher is wired (`fetcher_wired=true`) and a live fetch of GET-673 returns HTTP 200 with the issue; moreover the fetch is never reached for the exact text because extraction returns `[]` first.
- **Answer-text/generator issue** — ruled out as primary: the generator said "not in the context" honestly, because the vector context had no GET-673 passage; the deterministic #3307 facts line was never built because no key was named.

## Intent

1. A loose (spaced or fused) key mention fires when it is preceded (within the existing window) by a **field-question cue** asking about the ticket — at least `status`, `assignee`, `priority` (any case; plural forms at the executor's discretion). This is a widening of the existing context guard, same direction rule (cue must PRECEDE the key), same window, applied uniformly to every configured project key — no per-project dictionary.
2. Everything #3299 deliberately refuses still refuses: `can I get 2 volunteers?`, `tell me about DEMO 673` (existing fixture), context word only AFTER the number, bare numbers, unconfigured projects, glued forms. Key-free questions stay byte-identical (the #3299 parity receipt).
3. When the exact Telegram text is asked, the answer carries GET-673's live facts line (#3307 shape `GET-673 — Status: …`) from one bounded live fetch — no new fetch path, no new budget.
