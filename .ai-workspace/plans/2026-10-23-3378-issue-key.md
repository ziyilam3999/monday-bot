## ELI5

The bot has a fast lane for questions that name a ticket: it reads that exact ticket live from Jira and says its current status. To avoid mistakes, it only treats "demo 673" (with a space, no dash) as a ticket name when a word like "jira" or "ticket" comes just before it — because "demo" is also an everyday verb ("can I demo 2 volunteers?"). The operator asked "what's the status of demo 673?". No "jira" or "ticket" word, so the fast lane never opened; the question went to the ordinary search, which had no passage about DEMO-673, and the bot said it couldn't find it. The ticket is real (Jira returns it). The fix: the exact phrase "status of / assignee of / priority of" (or "for" / "on") right before the ticket name counts as enough context, while "can I demo 2 volunteers" or "our priority is to demo 2 hotfixes out" still do not.

Known limit, by design (tell the operator): "DEMO 673 status?" (the field word comes after) and "what is demo 673" (no field phrase) still will NOT open the fast lane — write "DEMO-673" with the dash, or "status of demo 673", or "jira demo 673".

## Root cause

The loose (spaced) shape `demo 673` is gated on a context word from `{jira, ticket, issue, key}` before the key; the operator's question carries a status cue ("status of") but none of those words, so `extractIssueKeys` returns `[]` and the exact-key leg never runs.

Alternatives ruled out by evidence:
- **Project-key allowlist** — ruled out: `DEMO` is configured (`DEMO_configured=true`, startup log `jira:DEMO indexed 898 issues`), and `demo-673` / `status of jira demo 673` both extract `DEMO-673`.
- **Jira fetch failure** — ruled out: the fetcher is wired (`fetcher_wired=true`) and a live fetch of DEMO-673 returns HTTP 200 with the issue; moreover the fetch is never reached for the exact text because extraction returns `[]` first.
- **Answer-text/generator issue** — ruled out as primary: the generator said "not in the context" honestly, because the vector context had no DEMO-673 passage; the deterministic #3307 facts line was never built because no key was named.

## Intent

1. A loose (spaced or fused) key mention also fires on a **field-question phrase** that sits IMMEDIATELY before the key: a field word (`status`, `assignee`, `priority`, any case) directly followed by one preposition from `of` / `for` / `on` (optionally `about`), with the key token right after that preposition — shape `<field> <prep> <KEY> <number>`, nothing else between — e.g. `status of demo 673`, `priority for DEMO 673`, `assignee on demo673`. A field word anywhere else in the window (`our priority is to demo 2 …`, `status update: demo 5 …`, `priority: demo 3 …`, `the assignee should demo 2 …`, `what's the status, can we demo 2 …`) does NOT count. The existing `{jira, ticket, issue, key}` window rule is unchanged; this is one added, adjacency-bound arm, applied uniformly to every configured project key — no per-project dictionary. (Plan-review r1 B1: a loose field word in the window false-fires, and a miss for a phantom key replaces the whole answer with the miss line — `service.ts` 386-390.)
2. Everything #3299 deliberately refuses still refuses: `can I demo 2 volunteers?`, `tell me about DEMO 673` (existing fixture), context word only AFTER the number, bare numbers, unconfigured projects, glued forms. Key-free questions stay byte-identical (the #3299 parity receipt).
3. When the exact Telegram text is asked, the answer carries DEMO-673's live facts line (#3307 shape `DEMO-673 — Status: …`) from one bounded live fetch — no new fetch path, no new budget.

The cost is larger than the Risks section says. In service.ts lines 386-390, a key Jira does not return (miss or timeout) with nothing pinned makes the reply ONLY the miss line. "Our priority is to demo 2 hotfixes out, what's blocking?" would then see "DEMO-2 not found" in place of a real answer. A DEMO-N that does exist gets pinned ahead of the real context, with its facts line placed first. The project key here is an everyday word, and status, priority and assignee are everyday words in a work chat. This is a new loss this ticket would introduce, not the registered `3299-word-context-guard` risk.

Example: `status of demo 673`, `status on DEMO 673`, `assignee of demo673`, `priority for Demo 673`. The existing `jira/ticket/issue/key` rule stays unchanged. This still fixes the operator's exact text (verified: `status of demo 673` and `status on demo 673` both have the cue+connector adjacent to the key).
