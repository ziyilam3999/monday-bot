The architecture (pure gate, gate-internal normalization, byte-identical non-matching path per the #3299 parity convention, one shared card source, zero-LLM arms, no ask-log line on cards) is sound and the ACs are externally checkable. Two dispatch-named protection classes fail on the spec as written.

1. **MAJOR (blocker) — P1 fires on leading paths/URLs; the dispatch's must-not-fire class has no arm.** Executed per B4 as written: `/api/v1/users what does this return` → card, `/etc/hosts` → card (and `/3.5 release notes…` likewise). B4 fires on ANY leading `/` that is not a registry-command-with-payload, so a pasted file path, API path, or slash-prefixed line — a real doc question today — gets the help card, zero retrieval, and (per B8) no ask-log line, i.e. a silently wrong answer plus an undercounted ask. The dispatch's check 1 names this class as must-stay-on-doc-path; the plan neither protects it nor names and accepts the trade. Fix within the plan's own shape: P1 fires only when the first token is command-shaped — one `/` followed solely by letters/digits/dash (`^\/[A-Za-z0-9][A-Za-z0-9-]*$`, no internal `/`), anything else with a leading slash → doc path — and add two leading-path arms to the P1 must-not-fire column (`/api/...`, `/etc/...` style).

2. **MAJOR (blocker) — "hello monday" (greeting + the bot's own name) does not fire.** Executed per the B5 lexicon/filler as written: `hello monday` → DOC (2 tokens, `hello` in lexicon, the name token in neither lexicon nor filler). This is the dispatch's own false-miss check and the exact bug class of the ticket (a greeting getting a doc lecture); the filler already contains `bot` but not the bot's name. Fix: add the bot's own name token(s) to the greeting filler (B10's exported constants). The all-tokens rule keeps question forms safe — `hello monday, what about annual leave` stays DOC because `what`/`about`/`annual`/`leave` are content — so the fix costs nothing on the regression side; add `hello <bot-name>` to the P2a must-fire column.

3. **MINOR — the shared card teaches commands that cannot work on Telegram, including one that loops.** The command-list body is Slack's registry: a Telegram user who follows `/status-monday` (bare registry → card) gets the card again, and `/sync-confluence ENG` (payload → doc path) gets a doc lecture about the space — teach-then-dead-end. B7's preamble ("questions work as plain messages") mitigates; make the Telegram preamble explicitly say the slash list is the Slack surface and plain-text questions are the Telegram way, so the card is truthful on the channel it renders on.

4. **NAMED-RISK NOTE (carried, not a blocker, per round-scope contract §2c)** — one-word messages that collide with a finite lexicon fire the card: `morning`, `good`, `sup` (P2a lexicon) and `commands`, `how does this work` (P2b probes) are all plausible whole-message doc queries and all fire under the spec. This is a theorem about finite match sets, not a defect of this plan; the ambiguity→doc doctrine already bounds it. Condition for execution-review: if the shipped lexicon/probe sets grow beyond the plan's exported constants, or a real ask-log `questionLen` pattern shows one-word doc asks getting cards, tighten then — do not add AC arms now.

5. **NIT — pin AC-7 identity by construction, not extraction.** "Command-list section string-identical" is only decidable if the test compares the B7 shared builder's rendered list as it appears in BOTH surfaces (import the builder, assert `helpCommand()` contains/delegates to its exact output and the Telegram card contains the same bytes), not by substring-slicing `helpCommand()` prose. B7 already implies this; say it in AC-7 so the test can't pass via a coincidental slice.
